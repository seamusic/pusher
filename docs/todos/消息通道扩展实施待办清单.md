## 1. 执行规则与范围

- 使用稳定任务编号跟踪提交与验证记录；只有对应交付物和验收证据齐备后才勾选任务。
- 默认范围是基础改造、已有队列缺陷修复、P0 三个 Type、P1 核心六个 Type。条件式 P1 和 P2 保留为待选任务，不作为默认批次完成条件。
- 已有 16 个 Type 是基线；P0 全部验收后预计为 19 个，P0 与 P1 核心全部验收后预计为 25 个。Server酱两版本、WxPusher 两模式各计一个 Type；实际数量随验收结果更新。
- 保留现有分层、`IChannelProvider`、Factory、DI、`Task SendAsync(...)`、Channel 表和现有对外 API。普通 HTTP 通道不预设数据库迁移；专项数据模型另行设计。
- 基础改造、已有缺陷修复、各 Provider 分开提交。共享代码发生变化时，先验证受影响的旧行为，再合入依赖它的新通道。
- 本文所有代码路径均相对仓库根目录（包含 `MessagePusher.slnx` 的目录）；本清单保存于 `docs/todos/`，源码直接位于仓库的 `src/`。
- 官方协议核验与真实送达分别记录。缺账号或未核实协议时，标记具体阻塞项，继续其他无依赖任务，不凭历史样例补造实现。
- 实施中如调整 Type、模式、范围或依赖，先同步原方案，再更新本清单；不静默提升 P2 优先级。

自动化验收必须检查以下行为，通道不适用项需在记录中说明理由：

1. stub 捕获最终请求 URL、路径/query、Header、Content-Type 和线上字段名/编码，不能只断言序列化前对象。
2. `Content` 为空时 fallback `Description`；URL 使用协议专有字段或追加正文且不重复；截断遵守通道限制并保留 Unicode 字符完整性，处理不修改输入消息。
3. 动态目标遵守 `To` 优先于 `AccountId`；固定目标拒绝非空 `To`，群组固定目标子通道使用空目标。多模式按模式分别验证。
4. 成功响应与失败响应均有样例；HTTP 2xx 下业务失败、非法 JSON 或缺必需成功信息不能被误判成功。非 2xx HTML 转为可读错误，空响应是否合法按协议判断。
5. 多目标接口检查逐目标结果；部分失败形成明确错误信息，不能只依据顶层 HTTP 200 宣告全部成功，也不对整批无条件重发。
6. 新增/编辑配置、API 直调、模式切换、Secret 留空保留与不回显、自托管 URL 策略和错误脱敏覆盖对应路径。
