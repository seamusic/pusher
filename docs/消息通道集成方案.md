## 1. 背景与目标

当前项目已完成从 Go（songquanpeng/message-pusher）到 .NET 的迁移，核心功能（用户、消息、Webhook、通道推送）均已落地。现有通道类型共 **16 种**，见下表。本方案的目标是：

1. **梳理尽可能多的可选通道**，形成一份可落地的集成清单；
2. **给出统一的集成模式**，让新增通道的成本降到最低；
3. **明确实施顺序与验收标准**，供评审与后续编码执行。

## 2. 现有通道抽象（关键约束）

本期 HTTP 推送通道保留现有分层、`IChannelProvider`、Factory 与 DI；扩展前完成 §6.2 的必要改造。Web Push、厂商推送等涉及订阅或设备管理的候选另做专项设计，不套用简单 Provider 的工作量估算。

### 2.1 核心接口

```csharp
// MessagePusher.Application.Abstractions.CoreAbstractions.cs
public interface IChannelProvider
{
    string Type { get; }   // 通道类型标识（如 "bark"、"telegram"）
    Task SendAsync(Message message, User user, Channel channel, CancellationToken ct);
}
```

- **工厂解析**：`ChannelProviderFactory` 按 `Type` 字符串从 DI 容器解析 Provider，未知类型抛 `UnsupportedChannelException`。
- **注册方式**：所有 Provider 以 `services.AddSingleton<IChannelProvider, XxxProvider>()` 注册（`Application/DependencyInjection.cs`），工厂自动收集。
- **数据模型**：`Channel` 实体已内置 6 个通用承载字段，新通道一般无需改表结构：

| 字段 | 用途 | 示例 | 回显策略 |
|------|------|------|----------|
| `Secret` | 密钥/Token | SendKey、AppToken | **不回显**（前端 `InputType.Password` + 后端清空返回） |
| `AppId` | 非敏感的应用/账号 ID | corpId、应用 ID | 回显 |
| `AccountId` | 目标账号/接收者 | Chat ID、UID | 回显 |
| `Url` | 服务器地址/Webhook | ntfy 服务器 | **回显**（因此禁止放凭证） |
| `Other` | 附加参数（JSON 或模板） | PushDeer 的 type 参数 | 回显 |
| `Token` | 通道维度鉴权令牌 | 与用户 Token 并列 | 回显 |

> **新增通道凭证约定**：第三方发送密钥存入 `Secret`，不得存入会回显的 `Url` / `Other` / `AppId`。`Token` 是 MessagePusher 自身的入站鉴权字段，不用于第三方认证。只需地址即可发送的 webhook（例如 Slack）应将**完整 webhook 地址存入 `Secret`**，或采用经明确设计的地址/密钥拆分；不能因字段名是 URL 就视为非敏感。[Slack 官方说明](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/)
>
> 自托管的 `Url` 只保存服务器地址；发送时允许按上游协议将 `Secret` 拼入请求路径，但日志和错误信息必须脱敏。Basic Auth 本期不做是范围选择，并非技术上必须将密码放入 URL。现有通道的历史凭证存放方式需另行梳理，不视作已满足上述新增通道约定。

### 2.2 发送上下文

`Message` 实体提供 `Title` / `Description` / `Content` / `Url` / `To` 等字段，`PushService.ProcessAsync` 会做统一前处理：

- `KeepCompatible` 兼容 `desp`/`short`/`openid` 旧字段；
- **Title 为空时**，`ProcessAsync` 会用 `SystemName` 填充 `message.Title`；
- `render_mode=code` 会把 `Content` 包裹成代码块。

Provider 负责将消息映射为上游请求，并判断业务响应；标题截断、正文 fallback、链接拼接等使用局部变量。GroupProvider 为每个子通道提供独立消息副本，避免子通道处理互相影响，详见 §6.2。原始消息的持久化与状态更新仍由发送流程负责。

## 4. 新增通道候选清单（按优先级）

按「场景覆盖 / 落地难度 / 与现有用户重合度」分为 P0、P1、P2；个人及自托管场景作为默认实施顺序，企业通道采用条件式 P1。

- P0、P1 核心通道给出协议、字段映射、目标覆盖和验收要点；尚未核实的内容明确列为待核验，不以猜测补齐。
- P2 是候选池，纳入清单不代表本期实现；同一 Provider 的不同接入模式不重复计算通道数。
- **资料核对日期：2026-09-19**。下列“已核对”仅指公开文档，不代表已使用真实账号验证送达；版本、额度和开通条件仍以编码时的官方页面为准。

### 4.0 统一发送约定（评审 #2、#4）

所有新增 Provider 必须遵守以下三条：

1. **目标覆盖约定**（评审 #2，仅适用于支持动态目标的通道）：
   ```csharp
   var dest = string.IsNullOrEmpty(message.To) ? channel.AccountId : message.To;
   ```
   现有 OneBot / Telegram / Group 均如此。`GroupProvider` 会把子目标写入 `message.To`，支持目标覆盖的 Provider 不能只读 `AccountId`。

   PushDeer、Gotify、息知、PushMe、WxPusher SPT、Chanify 以及固定 webhook 模式由凭证绑定目标，首版不支持 `To` 覆盖：前端说明限制；非空 `To` 返回可读业务错误，不静默忽略，也不将其当作发送密钥。配置群组时这类子通道的目标留空。Server酱³同样不将 `To` 映射为 Turbo 的 `channel`；其模式边界见 §4.1。

2. **正文 fallback 约定**（评审 #4）：`Channel.razor` 的测试消息只有 Title + Description、Content 为空。因此 `desp`/`content`/`message` 字段必须 fallback：
   ```csharp
   var body = string.IsNullOrEmpty(message.Content) ? message.Description : message.Content;
   ```

3. **URL 映射约定**（评审 #4）：按接口能力选择独立链接字段或追加正文。Server酱 / PushDeer / PushPlus / 息知 / PushMe 首版将 `message.Url` 追加到正文；ntfy 使用 `click`，WxPusher 标准模式与 Pushover 使用 `url`。同一链接不重复追加；纯文本与 Markdown 按各通道实际支持处理。

### P0 — 首期必做（国内主流、HTTP 简单、与 server酱/PushDeer 诉求直接对应）

#### 4.1 Server酱（Turbo + Server酱³，`server_chan`）

- **定位**：P0 保持一个 Type，兼容两个产品版本；两者账号和 Key 不通用。
- **认证与端点**：`Secret` 保存 SendKey，按格式识别版本。Turbo 的 `SCT...` 使用 `POST https://sctapi.ftqq.com/{sendkey}.send`；Server酱³的 `sctp<uid>t<token>` 提取数字 uid，使用 `POST https://{uid}.push.ft07.com/send/{sendkey}.send`。非法 Key 应在请求前报错，不将整个 Key 直接放进域名。
- **Content-Type**：官方支持 JSON/FORM；本方案选 `application/x-www-form-urlencoded`，复用 `PostFormAsync`。不能再写成“Server酱不支持 JSON”。
- **字段映射**：`Secret` ← SendKey；Turbo 模式 `AccountId` ← 可选 `channel`，允许 `To` 覆盖；Server酱³不支持该覆盖，`AccountId` 留空。`Other` 可保存非敏感 JSON 选项 `short`、`tags`，其中 `tags` 仅用于 Server酱³；跨模式不支持的选项应明确提示。
- **内容映射**：`title` ← Title；`desp` ← Content（空则 Description），末尾追加 Url。Turbo 标题按 32 字符限制处理，截断不得切断 Unicode 字符；Server酱³按其独立规则处理，不直接继承 Turbo 限制。
- **成功判断**：校验 HTTP 状态后，要求响应 JSON 的 `code == 0`；不假设两个版本的 `data` 结构完全一致。
- **额度与开通条件**：Turbo 官方当前说明为免费会员每天 5 条、订阅会员每天 1000 次 API 调用且每分钟不超过 50 条；Server酱³使用独立额度。Hint 按版本提示并附官方链接，不再写 Turbo 200 条/天。
- **核验来源**：[Server酱³文档](https://sc3.ft07.com/doc)、[官方 SDK](https://github.com/easychen/serverchan-sdk)、[Turbo 官方额度说明](https://sct.ftqq.com/pushbear/)；已核对公开说明，真实账号联调待实施。

#### 4.2 PushDeer（`pushdeer`）

- **定位**：开源、可自托管，支持 iOS/Android/微信/浏览器，与 server酱 同为高频诉求。
- **认证**：`pushkey`（**本期只做 pushkey，Basic Auth 自托管不做**）。
- **Content-Type**：本方案选择 `application/x-www-form-urlencoded`，使用 `PostFormAsync`。
- **发送 API**：
  ```
  POST {server}/message/push
  pushkey=<key>&text=<标题>&desp=<正文>&type=markdown
  ```
  返回 JSON `{ "code": 0, "content": {...} }`。
- **字段映射**：
  - `Secret` ← pushkey
  - `Url` ← 服务器地址，**默认 `https://api2.pushdeer.com`**（由 Provider 在发送时补默认值，覆盖 API 直建通道场景；现有 Bark 的默认值实际在前端提交时补齐）
  - `Other` ← 可选 `type=markdown|text`（**不含任何凭证**）
- **内容映射**：
  - `text` ← `message.Title`
  - `desp` ← `message.Content`（空则 `message.Description`）；`message.Url` 非空则追加
- **鉴权复杂度**：低。
- **目标与范围**：pushkey 绑定目标，不支持 `To` 覆盖；本期不扩展 Basic Auth 配置。自托管服务器地址遵守 §8 的出站 URL 策略。

#### 4.3 PushPlus（`push_plus`）

- **定位**：微信公众号推送，支持模板与群组；使用前需完成平台要求的实名认证。
- **认证**：`token`（个人中心获取）。
- **Content-Type**：`application/json`，复用现有 `PostRawAsync`。
- **发送 API**：
  ```
  POST https://www.pushplus.plus/send
  { "token": "...", "title": "...", "content": "...", "template": "markdown", "topic": "..." }
  ```
  返回 `{ "code": 200, "msg": "...", "data": "..." }`。
- **字段映射**：`Secret` ← token；`AccountId` ← topic（群组，遵循 §4.0 覆盖约定）；`Other` ← template。
- **内容映射**：`title` ← Title；`content` ← Content（空则 Description）；`message.Url` 非空则追加。
- **鉴权复杂度**：低。
- **额度提示**：当前微信渠道实名非会员用户每天 200 次请求，非会员接口频率每分钟 5 次；未实名认证无法调用发送接口，返回码为 `905`。请求次数不等于实际送达条数。Hint 同时写开通条件与额度，并链接[官方额度说明](https://pushplus.plus/doc/guide/use.html)。

### P1 — 第二期推荐（个人推送 / 自托管；企业通道按需求加入）

#### 4.4 WxPusher（`wx_pusher`，标准推送 + SPT）

- **定位**：支持手机、桌面及微信等接收方式；标准模式适合应用向用户/主题发送，SPT 模式适合个人脚本。
- **标准模式**：`POST https://wxpusher.zjiecode.com/api/send/message`，`application/json`；`Secret` ← appToken，`AccountId` ← UID（多个用 `|` 分隔），`Other` ← 非敏感 JSON 选项（mode、topicIds、contentType）。发送字段为 `appToken/content/summary/contentType/uids/topicIds/url`。
- **内容映射**：`content` ← Content（空则 Description），`summary` ← Title，`url` ← Url；`contentType=3` 表示 Markdown。成功判断除顶层 `code==1000` 外，必须检查官方响应 `data` 数组中各 UID/topicId 的 `code/status`；任一目标 `code!=1000` 或结果缺失/无效均应报错，不能只检查 HTTP 200。接口受理成功不代表最终送达。
- **目标覆盖**：标准模式 `To` 非空时使用其 UID 列表，并不再附加配置中的 topicIds，避免单次定向发送时仍广播到默认主题；`To` 为空时使用配置的 UID/topicIds。
- **SPT 模式补充**：`Other.mode = "spt"`，`Secret` ← SPT，`AccountId` 留空，不支持 `To` 覆盖。SPT 无需创建应用，不能作为 appToken 塞进标准模式请求；其独立端点、载荷、成功响应需在编码时依据专属文档核实。
- **核验来源**：[官方开发文档](https://wxpusher.zjiecode.com/docs/)、[官方文档仓库](https://github.com/wxpusher/wxpusher-docs)。已确认两种接入模式；SPT 协议细节和真实发送待实施核验。

#### 4.5 ntfy（`ntfy`）

- **定位**：可自托管或使用官方服务的 HTTP pub/sub 推送。
- **认证**：可配 `Authorization: Bearer <token>`；公开 topic 与受保护 topic 的权限不同，按服务器配置填写。
- **Content-Type 与端点**：优先使用 JSON，向**服务器根路径** POST，不向 `/{topic}` POST JSON。纯文本接口仍可作为以后扩展，当前无需新增 `PostTextAsync`。
  ```http
  POST https://ntfy.sh/
  Content-Type: application/json

  { "topic": "mytopic", "title": "标题", "message": "正文", "click": "https://example.com", "priority": 3 }
  ```
- **字段与内容映射**：`Url` ← 服务器（默认 `https://ntfy.sh`）；`AccountId` ← topic，允许 `To` 覆盖；`Secret` ← 可选 Bearer Token；`Other` ← priority/tags 等非敏感 JSON 选项。`title` ← Title，`message` ← Content（空则 Description），`click` ← Url。
- **成功判断**：依据 ntfy 的成功消息对象和错误结构处理，不能套用 `code == 0/200` 的统一 JSON 模型。JSON 标题避免依赖 HTTP Header 的中文编码支持。
- **核验来源**：[官方 JSON 发布接口](https://docs.ntfy.sh/publish/#publish-as-json)。

#### 4.6 Gotify（`gotify`）

- **定位**：自托管推送服务器，带 Web 管理台，App Token 模式，Android/浏览器。
- **认证**：App Token（`X-Gotify-Key` Header）。
- **发送 API**：
  ```
  POST https://gotify.example.com/message
  X-Gotify-Key: <appToken>
  { "title": "...", "message": "...", "priority": 5 }
  ```
- **字段映射**：`Url` ← 服务器地址；`Secret` ← appToken；`Other` ← priority。采用 JSON 请求，title ← Title，message ← 正文 fallback 并追加 Url；App Token 绑定应用，不支持 `To` 覆盖；参见[官方发送说明](https://gotify.net/docs/pushmsg)。
- **鉴权复杂度**：低。

#### 4.7 Pushover（`pushover`）

- **定位**：面向 iOS/Android/桌面的推送服务；客户端购买、试用及 API 额度以[官网](https://pushover.net/)为准，不在方案中写死价格。
- **认证**：`user` + `token`（App Token）。
- **Content-Type**：本方案选择 `application/x-www-form-urlencoded`，使用 `PostFormAsync`。
- **发送 API**：
  ```
  POST https://api.pushover.net/1/messages.json
  token=<app_token>&user=<user_key>&message=<正文>&title=<标题>
  ```
- **字段映射**：`Secret` ← appToken；`AccountId` ← userKey（遵循 §4.0 覆盖约定）。`message` ← 正文 fallback，`title` ← Title，`url` ← Url；成功判断要求 `status == 1`，不套用 `code`；参见[官方 API](https://pushover.net/api)。
- **鉴权复杂度**：低。

#### 4.8 息知（`xizhi`，P1）

- **分级理由**：补充国内个人微信通知选择，与已有 P0/P1 HTTP 推送的实现模式接近；作为 P1 候选合理，编码前需完成接口核验。
- **认证与拟定字段映射**：`Secret` ← 平台签发的 key；平台绑定接收者，`AccountId` 留空，不支持 `To` 覆盖；`Url` 不保存含 key 的完整发送地址。
- **内容映射**：`title` ← Title；`content` ← Content（空则 Description），追加 Url。首版按文本通知处理，Markdown 展示能力待核验。
- **协议状态**：官网历史索引展示 GET/POST、`title/content` 和 `https://xizhi.qqoq.net/{key}.send`，当前入口为 `https://xz.qqoq.net/`。本次读取当前页面仅得到 JavaScript 页面提示，**尚未确认当前发送域名、POST 编码、成功码、额度及维护状态**，历史样例不能直接作为生产端点。
- **编码准入**：从当前官方控制台/说明确认端点及请求格式，保存脱敏成功/失败响应样例，并完成一次真实发送；核验前不在前端开放该 Type，也不宣称已实现。若接口不可用，保留 P1 候选并先实施其他 P1 项。
- **来源与日期**：[息知官网](https://xz.qqoq.net/)，2026-09-19 检查；当前协议与可用性待核验。仅归档协议，不对未知额度作承诺。

#### 4.9 PushMe（`pushme`，P1）

- **分级理由**：Android 个人通知及自托管场景，服务对象和接口明确；优先于未明确具体实现的 `bark_android`。
- **认证与字段映射**：`Secret` ← push_key；`Url` ← 发送服务根地址（默认 `https://push.i-i.me`，自建服务填写其 HTTP API 地址）；`Other` ← `type`（首版 text/markdown）；`AccountId` 留空，不支持 `To` 覆盖。
- **发送 API**：首版采用官方示例的表单 POST，复用 `PostFormAsync`，不使用企微/钉钉/飞书兼容模式。
  ```http
  POST https://push.i-i.me/
  Content-Type: application/x-www-form-urlencoded

  push_key=<key>&title=<标题>&content=<正文>&type=markdown
  ```
- **内容与响应**：title ← Title，content ← 正文 fallback 并追加 Url。原生接口成功返回**纯文本 `success`**，其他文本为错误；先检查 HTTP 状态，再按原生文本协议判断，不能 JSON 反序列化或对任意 2xx 判成功。
- **范围与验收**：本期只做持久 push_key + 通知消息；临时密钥、数据小屏和机器人兼容模式后续再评估。真实联调包含默认/自建端点、通知权限及客户端后台运行情况；不承诺所有 Android 机型均能后台必达。
- **核验来源**：[官方接口](https://push.i-i.me/docs/index)、[使用指南](https://push.i-i.me/docs/guide)、[自建服务](https://push.i-i.me/docs/host)，已核对公开协议；额度按官方最新说明，未明确部分不写死。

新增通道 `foo` 按以下步骤接入；先满足 §7.1 的基础改造依赖。数据库字段与现有 API 保持兼容，类型明确的配置对象和第三方请求 DTO 放在应用层。

### 5.1 后端（Domain + Application + DI）

1. **`Domain/Constants.cs`** — 增加 `ChannelType.Foo = "foo"`。
2. **HTTP helper 扩展（P0 先做，评审 #1）**：
   - 现有 `PostRawAsync` 固定 JSON，**已经支持自定义 headers**；新增 JSON 通道使用明确的第三方 DTO 和出站序列化配置，不能无条件复用本项目 API 的 snake_case 配置。`PostJsonAsync<T>` 直接反序列化，不适合需要检查 HTTP 状态及原始响应的新增 Provider。
   - **新增 `PostFormAsync`**：`application/x-www-form-urlencoded`，接受 `IEnumerable<KeyValuePair<string,string>>` 或字典，内部用 `FormUrlEncodedContent`。
   - **暂不新增 `PostTextAsync`**：ntfy 采用 JSON 即可；仅在后续确有纯文本请求需求时增加。
   - `PostRawAsync` 与新增 `PostFormAsync` 可继续返回 `(HttpResponseMessage, string)`；helper 在读取异常时释放响应，正常返回后由 Provider 释放。请求格式与响应格式分别处理，PushMe 的表单请求可以返回纯文本。

## 6. 架构评估与必要改造

### 6.1 评估结论与保留范围

**结论：进行局部重构，保留现有架构主干。** P0、P1 核心以及 KOOK、Chanify 的主要差异仍是认证、配置和 HTTP 协议，现有策略式 Provider 足以承载；需要处理的是已经出现的职责耦合与扩展风险。

- 保留现有项目分层、`IChannelProvider + ChannelProviderFactory + DI`，本期继续使用 `Task SendAsync(...)`。
- 保留 Channel 表的通用字段和现有对外 API；应用层增加配置解析对象，无需为每个 HTTP 通道建表。
- 保留通道独立的认证、内容映射、业务响应解析；公共层只提取已存在的 HTTP 共性。
- 重构随通道接入分批实施，不以“先统一改写全部旧 Provider”作为新增通道的前置条件；共享代码有变更时必须验证受影响的旧通道。

### 6.2 本期必要改造

1. **隔离对外 API 与第三方接口的序列化规则——最迟在 WxPusher 接入前完成。**

   [HttpChannelHelpers](../src/MessagePusher.Application/Channels/HttpChannelHelpers.cs) 目前使用 [JsonDefaults](../src/MessagePusher.Application/Json/JsonDefaults.cs) 的 `SnakeCaseLower`。若将匿名对象直接交给 helper，`appToken/contentType/topicIds` 会变成 `app_token/content_type/topic_ids`，与 WxPusher 要求不符。

   新通道使用独立请求/响应 DTO，以 `[JsonPropertyName]` 固定线上字段名，并使用出站专用 `JsonSerializerOptions`；helper 允许显式传入该配置。新 DTO 可与 Provider 放在同一通道目录。保留本项目 API 的现有 snake_case 约定，旧 helper 调用按原规则兼容，逐项验证后再迁移，不能直接修改全局策略。

   依据：[WxPusher 官方接口](https://wxpusher.zjiecode.com/docs/)、[System.Text.Json 字段命名规则](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/customize-properties)。

2. **隔离每个子通道的消息对象——P0 前完成。**

   [GroupProvider](../src/MessagePusher.Application/Channels/SignedProviders.cs) 会修改同一 Message 的 To/Channel，再依次传给子通道；[DiscordProvider](../src/MessagePusher.Application/Channels/SimpleProviders.cs) 等现有实现也会修改 Content。因此组内顺序可能影响后续通道的内容或格式选择。

   最小改造为每个子通道从原始消息创建独立副本，再写入该副本的 To/Channel；副本保留必要的消息标识及内容字段。新增 Provider 通过局部变量做截断、格式转换和链接拼接。群组仍按现有顺序执行，不在本次引入并行发送；暂不将全部接口改成不可变 SendContext。

3. **补强 HTTP 基础处理——P0 前完成，后续通道复用。**

   扩展现有 helper 即可，支持 JSON/表单及自定义 Header，明确超时、取消、HTTP 状态与响应释放的责任；地址校验和脱敏使用共用逻辑。底层保留原始响应体，业务成功码、文本 success、消息对象等由对应 Provider 判断，错误信息不得泄漏凭证。

   不抽象通用业务响应模型，也不对全部 POST 自动重试。429、网络超时等先形成可读错误；是否重试需结合通道幂等与受理状态设计，避免把已受理但响应丢失的请求重复发送。

4. **增加类型明确的配置解析与后端校验——P0 建立入口，各新增通道随接入补齐。**

   [ChannelService](../src/MessagePusher.Application/Services/ChannelService.cs) 当前主要直接保存通用字段。应按 Type/模式解析为专属配置对象，检查必填项、取值范围、URL 和互斥参数；类型支持集合复用实际 Provider 注册，不增加独立维护的候选白名单。

   更新时先合并可保留的旧 Secret，再验证完整配置；跨 Type/模式不盲目继承旧密钥。已有编辑路径允许改变 Type，相关 Token 移除/新增也必须正确，不能继续仅按旧 Type 处理。此处修复编辑正确性；全面 Token 注册化与刷新策略仍按 §6.3 排期。历史 Other 中的标量、模板和复合字符串按原通道格式兼容，不批量改写存量配置。

### 6.3 按需实施的演进项

| 项目 | 触发时机 | 改造范围与边界 |
|------|----------|----------------|
| 轻量通道目录与能力描述 | P1 出现重复维护负担时 | 集中维护名称、模式、是否支持动态目标/自托管等；能力按 Type + 模式判断。可先合并现有定义，不以重写整套前端动态表单为前提 |

| 结构化发送结果 | 需要上游消息 ID、部分成功、查询回执或定向重试时 | 再评估 SendResult 与逐目标结果模型；本期继续使用 Task + 明确异常语义，调用受理成功不被解释为用户已收到 |

### 6.4 本期暂缓的改造

| 项目 | 决策 | 理由 |
|------|------|------|
| `GenericWebhookProvider` 或多层 Provider 基类 | 暂缓 | 共享传输已足够；认证、权限及业务响应仍有明显差异 |

### 6.5 已有缺陷修复：异步队列启动恢复阻塞

**性质：现有实现缺陷，单列修复；不属于新增通道要求的新架构。** 以下结论来自代码静态检查，尚未完成运行时回归或修复。

- **触发路径**：[AsyncMessageWorker](../src/MessagePusher.Application/Messaging/AsyncMessageWorker.cs) 在 ExecuteAsync 中先 await LoadPendingAsync，将待发消息全部入队，随后才启动消费；[AsyncMessageQueue](../src/MessagePusher.Application/Messaging/AsyncMessageQueue.cs) 容量为 128，满时等待。当前配置下，恢复 129 条及以上待发消息会在进入消费循环前等待队列空位。
- **消费者数量**：[DependencyInjection](../src/MessagePusher.Application/DependencyInjection.cs) 重复调用两次 `AddHostedService<AsyncMessageWorker>()`，框架使用 TryAddEnumerable，不能据此假定有两个消费者。[官方注册实现](https://github.com/dotnet/runtime/blob/main/src/libraries/Microsoft.Extensions.Hosting.Abstractions/src/ServiceCollectionHostedServiceExtensions.cs)
- **最小修复方向**：让回灌与消费能够同时推进，管理两者的任务生命周期、取消与错误传播；移除无效重复注册。若需要多消费者，显式配置并验证数量，不能靠增大容量或无界队列掩盖问题。
- **排期**：与基础改造同批安排，可独立提交；扩展通道的异步发送验收前完成。回归要求见 §7.3，不因该缺陷额外引入消息中间件。

### 7.2 每个通道的验收标准（Definition of Done）

**自动化测试（进 CI，评审 #5）**：

1. 单测用 `HttpMessageHandler` stub，断言：
   - 请求 URL（含路径/query）正确；
   - `Content-Type` 正确（form / json / text）；
   - 最终线上请求体字段名及映射正确（含 appToken/contentType/topicIds 等大小写、正文 fallback、URL 映射、dest 覆盖），不能只检查序列化前对象；
   - 各协议的成功响应正常返回（包括 PushMe 纯文本 `success`、Pushover status、ntfy 消息对象）；
   - HTTP 2xx 下业务错误或缺少协议必需成功信息时抛 `BusinessException`；空响应是否有效按各通道协议断言，不套用统一 code 判断；
   - HTTP 非 2xx（如 500 返回 HTML）时不因反序列化抛错、而是抛可读 `BusinessException`；
   - 动态目标覆盖正确；固定目标通道对非空 `To` 返回业务错误；群组的固定目标子通道以空目标调用正常；
   - Server酱两种 Key 的端点路由、非法 Key、跨模式参数和标题边界；WxPusher 标准/SPT 分支及单次目标不附加默认主题；
   - ntfy JSON 发往服务器根路径且支持中文标题；PushMe 原生响应不按 JSON 解析，非 success 文本不能判成功；
   - 新增/修改完整配置校验、Secret 保留与不回显、模式切换和不支持的 To 处理正确；错误信息不泄漏 Key 或 webhook 地址。

**手工联调清单（不进 CI）**：

2. 真实目标通道收到消息（标题、正文、URL 拼接正确）；
3. 前端下拉能选到该类型，表单字段/提示/额度文案正确，保存后回显（凭证字段除外）；
4. `Channel.razor`/`Login.razor`/README 数量与实际实现一致；自托管通道至少验证一次自建端点；息知补齐官方协议及脱敏响应记录。

### 7.3 基础改造与已有缺陷的回归验收

以下检查随对应改造进入自动化测试；使用 stub/fake HTTP、仓储和 Provider，不向真实通道发送测试消息。当前文档更新不代表这些测试已实现或通过。

| 改造项 | 必须覆盖的行为 |
|--------|----------------|
| 序列化隔离 | WxPusher 最终请求保留 appToken/contentType/topicIds，不能出现对应 snake_case 错名；本项目对外 API 及受影响的旧 Provider 保持既有字段契约 |
| 消息隔离 | 先发送会修改内容的子通道，再发送另一子通道，后者仍获得原始正文；交换顺序结果一致。原消息的 To/Channel/Title/Content 不被组内处理覆盖，固定目标与动态目标可混合使用 |
| HTTP 基础处理 | JSON 与表单正确编码中文及特殊字符；非 2xx 的 HTML 错误页可读处理；业务失败不因 HTTP 200 被忽略；请求超时/取消可结束等待，响应在正常和异常路径均释放；未显式启用重试时不重复发送 |
| 地址与凭证处理 | 自托管 HTTP 开关、默认地址和禁止本服务地址策略一致；异常及日志不包含密钥或完整敏感 webhook |
| 配置校验 | API 直调同样拒绝未知 Type、无效模式/目标/URL/参数；同模式留空 Secret 正确保留旧值且不回显；跨 Type/认证模式不误用旧密钥或 Token；状态单独更新及旧 Other 格式兼容 |
| 队列恢复缺陷 | 待恢复消息分别为 0、128、129 及更多时均能进入消费，并在有界测试超时内完成；验证运行中的消费者数量、回灌期间取消/异常与再次启动恢复；不因重复注册或重复回灌额外发送同一条待恢复消息 |

## 8. 风险与待确认事项

1. **平台开通与额度**：Hint 需同时提示开通条件、调用频率及额度。PushPlus 要求实名；Server酱按 Turbo/³区分；息知未核验的额度不得写死。
2. **资料与可用性分开记录**：官方页面可访问不代表服务已联调成功；息知的当前域名、编码、响应和维护状态尤其需要补核验。SPT 和 Chanify 的独立响应规则也需补实测样例。每个落地通道记录官方链接、核对日期及验证结果。
3. **协议差异**：PushMe 原生接口返回纯文本，ntfy/Pushover 不使用统一 code 模型；多目标通道须检查逐目标结果。接口受理成功不等于最终送达；本期不承诺统一送达回执，支持查询/回调的服务另行设计。
4. **凭证与出站地址**：第三方密钥及含密钥 webhook 存 Secret；节点 Url 不含凭证。新自托管通道（PushDeer、ntfy、Gotify、PushMe、Chanify）统一复用 ChannelUrlAllowNonHttps 策略：默认要求 HTTPS，仅在明确启用该开关时允许 HTTP；同时执行禁止指向本服务地址的校验。请求、响应和异常日志脱敏。
5. **场景边界**：KOOK 首版仅频道消息；QQ 官方机器人不等同 OneBot；Teams 采用 Workflows；PushMe 的接收效果需结合 Android 通知及后台权限验证。不能仅按“HTTP 简单”推断所有平台都可无条件主动推送。
6. **专项边界**：浏览器订阅、厂商设备 Token、短信模板和回执不纳入普通 Provider 的无迁移承诺。P2 先记录需求与设计，不提前注册到通道下拉。
7. **改造兼容性**：不能全局替换 snake_case 规则或将历史 Other 一律按新 JSON 格式读取；消息副本需保留必要上下文。按 §7.3 验证现有 API、受影响旧 Provider、群组和配置编辑。
8. **异步恢复与投递语义**：§6.5 的恢复阻塞作为已有缺陷修复；本期不承诺跨进程故障下的严格一次送达。统一重试、逐目标回执等能力待 §6.3 的结果模型与幂等设计明确后实施。

## 9. 结论与评审答复

- **首期范围**：保持 server_chan / pushdeer / push_plus 三个 Type；server_chan 同时覆盖 Turbo 与 Server酱³。P0 前完成消息隔离、HTTP 基础处理（含 PostFormAsync）和配置校验入口；PushDeer Basic Auth 仍不纳入本期。
- **新增分级**：采纳 P1 `xizhi`（息知）、`pushme`，P2 `kook`（KOOK，原开黑啦）、`chanify`。理由分别是国内个人通知与 Android 自托管补充、社群及苹果生态的按需扩展；息知需先完成当前协议核验。
- **覆盖补充**：WxPusher 增加 SPT；企业需求下将 Slack、Teams Workflows、钉钉应用通知列为条件式 P1；Qmsg、QQ 官方机器人、Web Push、短信及 Apprise 桥接列入 P2 候选。
- **架构结论**：保留分层、IChannelProvider、Factory、DI 及现有 Channel 表；通过局部重构处理实际扩展风险，最迟在 WxPusher 接入前完成出站序列化隔离。模式扩展不重复计数，待开发项不标为已实现。
- **演进边界**：轻量通道目录、Token 管理、结构化结果按需求推进；通用 Provider 大抽象、完整动态表单、凭证加密及部署架构调整暂缓。新数据模型的专项能力另行编写设计文档。
- **已有缺陷**：异步队列恢复阻塞独立修复，并在扩展通道异步验收前完成回归，不将修复描述为已完成，也不扩大为消息中间件替换项目。
