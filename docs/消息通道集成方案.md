## 1. 背景与目标

当前项目已完成从 Go（songquanpeng/message-pusher）到 .NET 的迁移，核心功能（用户、消息、Webhook、通道推送）均已落地。现有通道类型共 **16 种**，见下表。本方案的目标是：

1. **梳理尽可能多的可选通道**，形成一份可落地的集成清单；
2. **给出统一的集成模式**，让新增通道的成本降到最低；
3. **明确实施顺序与验收标准**，供评审与后续编码执行。

## 2. 现有通道抽象（关键约束）

新增通道必须遵循现有架构约定，无需也不应推翻现有抽象。

### 2.1 核心接口

```csharp
// MessagePusher.Application.Abstractions.CoreAbstractions.cs
public interface IChannelProvider
{
    string Type { get; }   // 通道类型标识（如 "bark"、"telegram"）
    Task SendAsync(Message message, User user, Channel channel, CancellationToken ct);
}
```

- **工厂解析**：`ChannelProviderFactory` 按 `Type` 字符串从 DI 容器解析 Provider，未知类型抛 `UnsupportedChannelException`。
- **注册方式**：所有 Provider 以 `services.AddSingleton<IChannelProvider, XxxProvider>()` 注册（`Application/DependencyInjection.cs`），工厂自动收集。
- **数据模型**：`Channel` 实体已内置 6 个通用承载字段，新通道一般无需改表结构：

| 字段 | 用途 | 示例 | 回显策略 |
|------|------|------|----------|
| `Secret` | 密钥/Token | SendKey、AppToken | **不回显**（前端 `InputType.Password` + 后端清空返回） |
| `AppId` | 应用/账号 ID | corpId、PushDeer key | 回显 |
| `AccountId` | 目标账号/接收者 | Chat ID、UID | 回显 |
| `Url` | 服务器地址/Webhook | ntfy 服务器 | **回显**（因此禁止放凭证） |
| `Other` | 附加参数（JSON 或模板） | PushDeer 的 type 参数 | 回显 |
| `Token` | 通道维度鉴权令牌 | 与用户 Token 并列 | 回显 |

> **⚠️ 关键约定（评审 #3）**：`Url` 与 `Other` 会回显到前端（现有代码只对 `Secret` 做不回显处理），因此**任何凭证（账号/密码/token）一律只能放 `Secret`，禁止放入 `Url` 或 `Other`**。自托管通道的 Basic Auth 账号密码本期不做（见 §4.2）。

### 2.2 发送上下文

`Message` 实体提供 `Title` / `Description` / `Content` / `Url` / `To` 等字段，`PushService.ProcessAsync` 会做统一前处理：

- `KeepCompatible` 兼容 `desp`/`short`/`openid` 旧字段；
- **Title 为空时**，`ProcessAsync` 会用 `SystemName` 填充 `message.Title`；
- `render_mode=code` 会把 `Content` 包裹成代码块。

Provider 只需关心「如何把 message 内容映射到目标通道的请求」。

### 2.3 前端联动点（新增通道必改之处）

| 文件 | 位置 | 内容 |
|------|------|------|
| `MessagePusher.Web/Api/Models.cs` | `ChannelTypes.All` 数组 | 通道类型下拉选项（Value + 显示名） |
| `MessagePusher.Web/Components/Pages/ChannelEdit.razor` | `Fields(type)` switch | 该通道的配置表单字段 |
| `MessagePusher.Web/Components/Pages/ChannelEdit.razor` | `Hint(type)` switch | 该通道的填写提示文案（**含免费额度提示**） |
| `MessagePusher.Web/Components/Pages/Channel.razor` | 页头 `Description` | 硬编码「16 种消息通道」→ 更新数量 |
| `MessagePusher.Web/Components/Pages/Login.razor` | 副标题 | 硬编码「16 种通道」→ 更新数量 |

> 评审 #6：`Channel.razor`（第 11 行）与 `Login.razor`（第 17 行）写死了「16 种」，新增通道后必须同步更新，否则文案与实际不符。

## 4. 新增通道候选清单（按优先级）

下面按「热度 / 落地难度 / 与现有用户重合度」分成三档。每条通道都给出：**Type 标识、认证方式、Content-Type、发送 API、字段映射、内容映射、鉴权复杂度**。

### 4.0 统一发送约定（评审 #2、#4）

所有新增 Provider 必须遵守以下三条：

1. **目标覆盖约定**（评审 #2）：
   ```csharp
   var dest = string.IsNullOrEmpty(message.To) ? channel.AccountId : message.To;
   ```
   现有 OneBot / Telegram / Group 均如此。`GroupProvider` 会把子目标写入 `message.To`，因此若新通道只读 `AccountId`，群组通道与单次指定目标都会失效。

2. **正文 fallback 约定**（评审 #4）：`Channel.razor` 的测试消息只有 Title + Description、Content 为空。因此 `desp`/`content`/`message` 字段必须 fallback：
   ```csharp
   var body = string.IsNullOrEmpty(message.Content) ? message.Description : message.Content;
   ```

3. **URL 拼接约定**（评审 #4）：server酱 / PushDeer / PushPlus 均**无独立 URL 字段**，`message.Url` 需拼进正文（追加到 desp/content 末尾），Bark 才有独立 `url` 字段可单独传。

### P0 — 首期必做（国内主流、HTTP 简单、与 server酱/PushDeer 诉求直接对应）

#### 4.1 server酱（Server酱 Turbo，`server_chan`）

- **定位**：国内最普及的「一个 HTTP 请求 = 一条微信消息」，本项目用户提及的刚需。
- **认证**：SendKey（`SCT` 开头），无需其他凭证。
- **Content-Type**：`application/x-www-form-urlencoded`（**不能用 `PostRawAsync`**）。
- **发送 API**：
  ```
  POST https://sctapi.ftqq.com/{SENDKEY}.send
  title=<标题>&desp=<Markdown正文>&channel=<可选通道>
  ```
  返回 JSON `{ "code": 0, "message": "...", "data": {...} }`，`code == 0` 表示成功。
- **字段映射**：
  - `Secret` ← SendKey（`SCT...`）
  - `AccountId` ← 可选接收通道（Turbo 通道号，可留空）；发送时遵循 §4.0 目标覆盖约定（单次指定 channel 用 `message.To`）
- **内容映射**：
  - `title` ← `message.Title`（**长度限制约 32 字符，超出截断**）
  - `desp` ← `message.Content`（空则 `message.Description`）；若 `message.Url` 非空，追加换行 `\n\n` + url
- **鉴权复杂度**：低。单一密钥。
- **额度提示**：免费版 5 条/天，Turbo 200 条/天（写入 Hint）。

#### 4.2 PushDeer（`pushdeer`）

- **定位**：开源、可自托管，支持 iOS/Android/微信/浏览器，与 server酱 同为高频诉求。
- **认证**：`pushkey`（**本期只做 pushkey，Basic Auth 自托管不做**）。
- **Content-Type**：`application/x-www-form-urlencoded`（**不能用 `PostRawAsync`**）。
- **发送 API**：
  ```
  POST {server}/message/push
  pushkey=<key>&text=<标题>&desp=<正文>&type=markdown
  ```
  返回 JSON `{ "code": 0, "content": {...} }`。
- **字段映射**：
  - `Secret` ← pushkey
  - `Url` ← 服务器地址，**默认 `https://api2.pushdeer.com`**（对齐 Bark 在发送时填默认 URL 的做法：`Url` 为空则用默认值，避免用户必填）
  - `Other` ← 可选 `type=markdown|text`（**不含任何凭证**）
- **内容映射**：
  - `text` ← `message.Title`
  - `desp` ← `message.Content`（空则 `message.Description`）；`message.Url` 非空则追加
- **鉴权复杂度**：低。
- **明确不做**：自托管 Basic Auth（会把账号密码塞进 `Url`，导致回显泄漏）。需自托管鉴权的用户建议用 ntfy（§4.5，token 走 `Secret` + header）。

#### 4.3 PushPlus（`push_plus`）

- **定位**：微信公众号推送，免费额度高（200 条/天），支持模板，国内用户常用。
- **认证**：`token`（个人中心获取）。
- **Content-Type**：`application/json`（可用 `PostRawAsync`，但建议统一走新 helper）。
- **发送 API**：
  ```
  POST https://www.pushplus.plus/send
  { "token": "...", "title": "...", "content": "...", "template": "markdown", "topic": "..." }
  ```
  返回 `{ "code": 200, "msg": "...", "data": "..." }`。
- **字段映射**：`Secret` ← token；`AccountId` ← topic（群组，遵循 §4.0 覆盖约定）；`Other` ← template。
- **内容映射**：`title` ← Title；`content` ← Content（空则 Description）；`message.Url` 非空则追加。
- **鉴权复杂度**：低。
- **额度提示**：免费版 200 条/天（写入 Hint）。

### P1 — 第二期推荐（自托管 / 通用性强，可作为差异化能力）

#### 4.4 WxPusher（`wx_pusher`）

- **定位**：公众号推送，支持一对多、二维码关注、带 UI 管理。
- **认证**：`appToken`（管理后台获取）。
- **发送 API**：
  ```
  POST https://wxpusher.zjiecode.com/api/send/message
  { "appToken": "...", "content": "...", "summary": "...", "contentType": 3, "uids": ["UID_xxx"], "topicIds": [...] }
  ```
- **字段映射**：`Secret` ← appToken；`AccountId` ← UID（多个用 `|` 分隔，遵循 §4.0 覆盖约定）；`Other` ← topicIds（JSON）。
- **鉴权复杂度**：低-中（需理解 UID/topic 两种定向）。

#### 4.5 ntfy（`ntfy`）

- **定位**：极简 HTTP pub/sub，32k+ star，可自托管或官方 `ntfy.sh`，支持 iOS/Android/浏览器。
- **认证**：默认开放；可配 `Authorization: Bearer <token>`。
- **Content-Type**：纯文本 body（**不能用 `PostRawAsync`，需 `PostTextAsync` + 自定义 header**）。
- **发送 API**：
  ```
  POST https://ntfy.sh/{topic}
  body=正文（纯文本），X-Title / X-Priority / X-Tags 等 Header
  ```
- **字段映射**：
  - `Url` ← ntfy 服务器（默认 `https://ntfy.sh`）
  - `AccountId` ← topic（遵循 §4.0 覆盖约定）
  - `Secret` ← Bearer 访问令牌（可选，走 header，不回显）
- **鉴权复杂度**：低。标题需通过自定义 Header 传递，需在 helper 层扩展 text+header 能力。

#### 4.6 Gotify（`gotify`）

- **定位**：自托管推送服务器，带 Web 管理台，App Token 模式，Android/浏览器。
- **认证**：App Token（`X-Gotify-Key` Header）。
- **发送 API**：
  ```
  POST https://gotify.example.com/message?token=<appToken>
  { "title": "...", "message": "...", "priority": 5 }
  ```
- **字段映射**：`Url` ← 服务器地址；`Secret` ← appToken；`Other` ← priority。
- **鉴权复杂度**：低。

#### 4.7 Pushover（`pushover`）

- **定位**：老牌付费推送（$4.99/平台买断），iOS/Android/桌面，稳定可靠，国际化用户常用。
- **认证**：`user` + `token`（App Token）。
- **Content-Type**：`application/x-www-form-urlencoded`（**不能用 `PostRawAsync`**）。
- **发送 API**：
  ```
  POST https://api.pushover.net/1/messages.json
  token=<app_token>&user=<user_key>&message=<正文>&title=<标题>
  ```
- **字段映射**：`Secret` ← appToken；`AccountId` ← userKey（遵循 §4.0 覆盖约定）。
- **鉴权复杂度**：低。

## 5. 统一集成模式（新增一个通道的标准步骤）

新增通道 `foo` 需改动以下文件，模式高度模板化。

### 5.1 后端（Domain + Application + DI）

1. **`Domain/Constants.cs`** — 增加 `ChannelType.Foo = "foo"`。
2. **HTTP helper 扩展（P0 先做，评审 #1）**：
   - 现有 `HttpChannelHelpers` 只有 `PostRawAsync`（固定 `application/json`）和 `PostJsonAsync`。
   - **新增 `PostFormAsync`**：`application/x-www-form-urlencoded`，接受 `IEnumerable<KeyValuePair<string,string>>` 或字典，内部用 `FormUrlEncodedContent`。
   - **新增 `PostTextAsync`**（P1 ntfy 用）：纯文本 body + 自定义 header（`X-Title` 等）。
   - 三者都返回 `(HttpResponseMessage, string)`，由 Provider 自行判断状态码与响应体。
3. **新建 Provider 文件**（评审 #7，**不要继续塞进 `SimpleProviders.cs`**）：
   - 新建 `Application/Channels/HttpPushProviders.cs`（P0 三通道集中放，或每通道一文件，二选一，推荐前者便于 review）；
   - 实现 `IChannelProvider`，`Type => ChannelType.Foo`；
   - 用 `IHttpClientFactory`（命名客户端 `"channels"`）发起请求；
   - 复用 `PostFormAsync` / `PostRawAsync` / `PostTextAsync`；
   - 发送目标遵循 §4.0 `dest = IsNullOrEmpty(message.To) ? channel.AccountId : message.To`；
   - 正文遵循 §4.0 fallback Description + url 追加；
   - **非 2xx 时先读状态码再处理**（评审 #5）：`if (!resp.IsSuccessStatusCode) throw ...`，不要对可能返回 HTML 的错误页做 JSON 反序列化；
   - 成功码校验（`code == 0` / `code == 200`），失败抛 `BusinessException`（带可读中文信息）。
4. **`Application/DependencyInjection.cs`** — 注册 `services.AddSingleton<IChannelProvider, FooProvider>()`。
5. **`ChannelService.AddAsync` 增加 Type 校验**（评审 #6）：维护一个已知 Type 集合（可与 `ChannelTypes` 定义对齐，或后端 `ChannelType` 常量清单），非已知 Type 直接抛 `BusinessException("未知的通道类型")`，避免前端绕过写进非法 Type。

### 5.2 前端（Web）

6. **`Api/Models.cs`** — `ChannelTypes.All` 追加 `("foo", "Foo 通道")`。
7. **`ChannelEdit.razor`** — `Fields(type)` 追加 `"foo" => [F(...), ...]`（表单字段，凭证字段一律 `secret: true`）。
8. **`ChannelEdit.razor`** — `Hint(type)` 追加 `"foo" => "..."`（提示文案，**含免费额度提示**，避免误判故障）。
9. **`Channel.razor`** 与 **`Login.razor`** — 更新硬编码的通道数量文案「16 种」→「N 种」（评审 #6）。

### 5.3 测试

10. **`tests/MessagePusher.Application.Tests`** — 为 Provider 增加单元测试，用 `HttpMessageHandler` stub（评审 #5），**不发起真实网络请求**。

### 5.4 文档

11. 更新本方案文档的「已实现通道清单」。

> 无数据库迁移：`Channel` 表结构不变，仅新增 `ChannelType` 字符串枚举，无 schema 变更。

## 6. 架构优化项（评审结论：本期全部不做）

| 项 | 结论 | 原因 |
|----|------|------|
| `GenericWebhookProvider` 抽象 | **不做** | Discord（204）与 Corp（errcode）响应语义不同构；只有 P2 的 Slack 等才可能复用，过早抽象只会增加理解成本 |
| 通道元数据化 | **不做** | 需前端表单渲染重构，投入大，与方案一致留作演进项 |
| Secret 加密存储 | **不做，不阻塞** | `CryptoServices` 只有 BCrypt 单向哈希，无法加密；真要加密需 Data Protection / AES，属独立 ADR |

> **安全底线（已纳入 §2.1 约定）**：敏感凭证只进 `Secret`（不回显），禁止放 `Url`/`Other`；额度写进对应 Hint，避免误判故障。

## 7. 实施计划与验收标准

### 7.1 分批实施建议

| 批次 | 通道 | 说明 |
|------|------|------|
| 第一批（P0） | server_chan、pushdeer、push_plus | 3 个国内主流 HTTP 通道，先打通闭环；**先补 `PostFormAsync` helper** |
| 第二批（P1） | ntfy、gotify、pushover、wx_pusher | 自托管 + 国际化，验证 `PostTextAsync` + header 模式 |
| 第三批（P2，可选） | slack、mattermost、matrix 等 | 视需求，届时再评估 `GenericWebhookProvider` |

### 7.2 每个通道的验收标准（Definition of Done）

**自动化测试（进 CI，评审 #5）**：
1. 单测用 `HttpMessageHandler` stub，断言：
   - 请求 URL（含路径/query）正确；
   - `Content-Type` 正确（form / json / text）；
   - 请求体字段映射正确（title/desp/content/url fallback、dest 覆盖）；
   - 成功码（`code == 0` / `code == 200`）时正常返回；
   - 非成功码（`code != 0`）时抛 `BusinessException`；
   - HTTP 非 2xx（如 500 返回 HTML）时不因反序列化抛错、而是抛可读 `BusinessException`；
   - 目标覆盖：`message.To` 非空时覆盖 `AccountId`，为空时用 `AccountId`。

**手工联调清单（不进 CI）**：
2. 真实目标通道收到消息（标题、正文、URL 拼接正确）；
3. 前端下拉能选到该类型，表单字段/提示/额度文案正确，保存后回显（凭证字段除外）；
4. `Channel.razor`/`Login.razor` 通道数量文案已更新。

## 8. 风险与待确认事项

1. **免费额度限制**：server酱免费版 5 条/天、PushPlus 200 条/天等，已要求写进 Hint 提示用户，避免误判为通道故障。
2. **第三方 API 稳定性**：API 地址/字段可能调整，**编码前必须再对一次各服务最新官方文档（域名、字段名）**（评审明确要求）。
3. **自托管凭证安全**：PushDeer Basic Auth 已移出 P0；ntfy/Gotify 的 token 走 `Secret` + header（不回显），不落 `Url`。
4. **出站 URL 策略**（评审 #3，需在编码时定）：自托管常是局域网 HTTP，不能直接套 `CustomProvider` 的「HTTPS-only」策略。需明确：是否复用 `ChannelUrlAllowNonHttps` 开关、是否禁止指向本服务地址（`CustomProvider` 已有此防护）。**建议**：自托管通道（ntfy/Gotify/PushDeer）默认允许 HTTP，但保留 `ChannelUrlAllowNonHttps` 关闭时的强制 HTTPS；所有自托管通道统一复用「禁止指向本服务地址」校验。

---

## 9. 结论与评审答复

- 现有 `IChannelProvider` 抽象已经非常适合扩展，**新增通道无需改表、无需改 `ChannelService`**（仅需在 `AddAsync` 增加已知 Type 校验），核心是「常量 + Provider + DI 注册 + 前端多处映射」。
- 建议**首期落地 server酱 / PushDeer / PushPlus 三个 P0 通道**，编码前先补 `PostFormAsync` helper。

**对方案第 9 节三项决策的最终答复（评审已确认）**：

1. **P0 范围**：认可 `server_chan` / `pushdeer` / `push_plus`；PushDeer 自托管 Basic Auth 移出 P0；Type 沿用现有 snake_case，无需别名；编码前再对官方文档。
2. **GenericWebhookProvider**：不做，P1 完成后再看 Slack 等是否值得抽。
3. **凭证加密**：不阻塞；敏感只进 `Secret`（不回显），禁止放 `Url`/`Other`；额度写进对应 Hint。
